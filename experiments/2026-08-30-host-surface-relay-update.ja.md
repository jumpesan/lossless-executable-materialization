# ホスト内部の中継転送に関する検証更新 — 2026-08-30

[英語版](2026-08-30-host-surface-relay-update.md)

## 状態

```text
研究 = Lossless Executable Materialization（損失のない実行ファイル実体化）
更新種別 = 公開用ホスト統合証拠の同期
プロトコル状態 = 候補 / 未標準化
本番状態 = 汎用的な信頼済みホスト統合は未確立
新規性の主張 = 未確立
主張範囲 = 観測したホスト / モデル環境に限定
```

この更新では、完全一致の実行ファイル実体化を汎用LLMホストへ統合する過程で見つかった、新しい境界を記録する。

元になったアプリケーション分野、非公開リポジトリのパス、ユーザーデータ、アプリケーション固有の状態名は意図的に除外している。実行カプセルなどの試料は、アプリケーション由来ではあるが内容を公開しない不透明な成果物として扱う。ここでは、プロトコル評価に必要な転送上の同一性情報とブラックボックス観測だけを報告する。

`v0.1-preliminary`タグは、固定された過去のスナップショットとして維持する。

---

## 1. 新しい境界: ホストで観測できても実行環境側で利用できるとは限らない

これまでの研究では、意味的なソース再構成によって挙動を維持できても、正本のバイト同一性を失う場合があることを確認した。

その後の信頼済みホスト統合では、これとは別の問題が現れた。

```text
ホストでリソースを観測できる
!=
呼び出し側 / モデル側コンテキストで完全一致のオペランドを利用できる
!=
実行環境側で完全一致バイト列を利用できる
```

ホストは、ある取得経路を通じて転送用リソースを正常に観測できても、コード実行用サンドボックスが同じ完全一致バイト列を独立して取得または受信できるとは限らない。

これは転送 / 実体化の境界であり、実行ファイルの認可そのものではない。

---

## 2. H1 — 外部リソースは観測できるが、サンドボックスへの完全一致引き渡しは成立しない

変更不能な転送記述子を直接指定したところ、ホスト側の取得経路では正常に解決できた。

観測結果:

```text
記述子の解決 = PASS
外部転送リソースの観測 = PASS
正本実行ファイルの同一性認識 = PASS
所有側入力の同一性観測 = PASS
意味的な再実装 = 未使用
正本実行 = 未完了
```

残った障害は次だった。

```text
ホストから見える転送ペイロード
-> サンドボックス内の完全一致バイト列
```

ホストは外部の転送データを読み取ることができ、別途Pythonも実行できた。しかし、現在のホスト機能では、その2つの能力の間に完全一致データを確実に受け渡す経路がなかった。

分類:

```text
H1_EXTERNAL_RESOURCE_TO_EXECUTION_SURFACE_HANDOFF = BLOCKED / OBSERVED
```

この結果により、問題の中心が実行ファイル選択や正本同一性の曖昧さではなく、ホスト内部のデータ引き渡しにあることが明確になった。

---

## 3. H2 — ローカル添付経路では正本実行がPASS

次に、同じ不透明な実行カプセルをウェブからサンドボックスへ転送するのではなく、ローカル添付経路から直接利用できる状態にした。

新規の分離セッションで次を確認した。

```text
GPT-5.6 Instant = 正本実行 PASS
GPT-5.6 High    = 正本実行 PASS
実行中のリポジトリ / ネットワーク取得 = 不要
```

実行経路では、転送表現を検証し、正本実行ファイルを再構成し、完全同一性を確認した後に呼び出し、構造化結果を受理した。

同じ完全一致カプセルを使って、所有側入力が意味的に不正となる代表的な否定系も実行した。

```text
正本の実体化 = PASS
正本呼び出し = PASS
受理対象のプロセス終了 = true
構造化された否定結果 = PASS
会話上の判断で成功状態へ昇格 = なし
```

代表的な結論:

```text
実行転送経路が利用できるかどうか
!=
推論レベル
```

少なくとも、この限定されたゲートではこの分離が成立した。

ローカル添付経路は実験上の証拠であり、一般利用者に実行基盤の内部管理を要求する方式を最終製品経路として採用したわけではない。

## 4. H3 — 大きな単一データによる呼び出し側コンテキスト中継はFAIL

次の候補では、実行カプセルを利用者が手動添付する必要をなくすことを試みた。

変更不能なステージング対象に、実行カプセル全体を1つの大きな符号化文字列として格納した。

代表的な形状:

```text
1行のステージング対象 ~= 13.2 KB
実行カプセルの完全一致符号化文字列 = 10944文字
復号後カプセルの目標サイズ = 8207バイト
```

想定した経路:

```text
ホスト / 呼び出し側で変更不能リソースを解決
-> 呼び出し側コンテキストで完全一致文字列を利用可能にする
-> 文字列リテラルとしてサンドボックスへ転送
-> ローカルで完全一致カプセルを再構成
```

実際の観測:

```text
ステージング対象の認識 = 一部のみ
完全一致の全文字列を呼び出し側コンテキストで利用 = 未確立
サンドボックスからのネットワーク再取得試行 = 観測
サンドボックスのネットワーク解決 = 失敗
ローカルでの完全一致カプセル配置 = 未到達
正本実行 = 未到達
```

その後、正本検証より前に所有側入力を意味的に解釈し始める挙動も観測され、これは限定した検証契約の範囲外だった。

分類:

```text
大きな単一データによる呼び出し側コンテキスト中継 = FAIL
実行環境側からの再取得への切替 = 経路逸脱
意味的な再実装へ向かう圧力 = 観測
```

このため、同じ大きな単一表現をそのまま再試行するのではなく、このホスト環境では不採用とした。

## 5. H4 — 小分けチャンクによる呼び出し側コンテキストからのリテラル中継はPASS

次の検証では、転送する内容自体は変えず、中継単位の大きさだけを変更した。

同じ完全一致の符号化カプセルを、小さな完全一致チャンクへ分割した。

```text
チャンク数 = 8
各チャンクのデータ長 = 1368文字
結合後の符号化長 = 10944文字
復号後カプセルサイズ = 8207バイト
復号後カプセルSHA-256 =
ecbe9641f9569c10d00b380de9f7bb1d28b0cbc564dabaa0dc499347f70e1e7f

正本実行ファイルサイズ = 20541バイト
正本実行ファイルSHA-256 =
0a363c3f88c9b5585567a846384984bbbd81bf2cf314f8e21a08d89c05cd2331
```

必須とした経路:

```text
ホスト / 呼び出し側で小さい完全一致チャンクを解決
-> 完全一致チャンク文字列をサンドボックス入力へリテラルとして渡す
-> サンドボックスからURL / ネットワーク / リポジトリを再取得しない
-> 宣言順に決定論的に結合
-> 転送対象全体の完全同一性を証明
-> 正本実行ファイルの完全同一性を証明
-> 正本を実行
```

最終的な限定判定:

```text
呼び出し側での小チャンク解決 = PASS
呼び出し側コンテキスト -> サンドボックスのリテラル中継 = PASS
サンドボックスからのネットワーク / 再取得回避 = PASS
完全一致カプセル再構成 = PASS
カプセル同一性検証 = PASS
正本実行ファイル同一性検証 = PASS
正本実行 = PASS
構造化結果 = PASS
```

### 証拠の整合確認

1回目の成功実行では、意図したリテラル中継経路と正本実行を画面上で確認できたが、表示されたチャンク長の1つが、その後に示された正確な合計長と矛盾していた。

同じ変更不能候補に対する2回目の実行で、決定論的な同一性情報を再確認した。

```text
チャンク長 = 1368 x 8
結合後長 = 10944
復号後サイズ = 8207
復号後SHA-256 = 完全一致
正本実行ファイル同一性 = 完全一致
正本実行結果 = PASS
```

ただし、2回目の実行では、ホストのアクティビティ表示が実行全体ではなく前半部分だけを表示した。

そのため、H4の最終判定では、同じ変更不能候補に対する2回の収束した証拠を組み合わせている。

```text
実行A = 画面上でリテラル中継 + 正本実行を確認
実行B = 完全一致の転送同一性を再確認
H4 = 限定条件下の複合証拠によるPASS
```

単一実行の完全な追跡情報を独立に確認できた場合より証拠強度が低いことを、明示的に開示する。

## 6. 条件比較

| 条件 | ホストでのリソース観測 | 実行環境側への完全一致転送 | 正本実行 | 分類 |
|---|---:|---:|---:|---|
| 外部転送データを直接利用 | PASS | BLOCKED | 未到達 | H1 否定観測 |
| ローカル添付経路 | ローカル | PASS | PASS | H2 肯定 |
| 1つの大きな呼び出し側ステージング対象 | 一部 | FAIL | 未到達 | H3 否定 |
| 8個の小さい呼び出し側リテラル | PASS | PASS | PASS | H4 限定的な複合証拠による肯定 |

この対照比較は、ホスト境界について次の解釈を支持する。

```text
損失のない転送表現が存在する
!=
ホストが必要な取得経路でその表現を利用可能にする
!=
ホストがその完全一致表現を実行基盤へ中継できる
```

## 7. 推定: 実行環境側への転送は独立したプロトコル境界である

現在の証拠は、ホストの取得経路と実行環境が分かれている場合に、任意のプロトコル段階として次を追加することを支持する。

```text
実行ファイルの認可
-> 損失のない転送表現
-> 転送表現の取得
-> 実行環境側への転送
-> 転送表現の同一性検証
-> 機械的な実体化
-> 完全同一性の証明
-> 実行資格
```

この転送段階は認可を生成しない。

```text
中継転送成功 != 実行ファイルの認可
転送チャンク != 実行ファイルの認可
ローカル添付 != 実行ファイルの認可
```

認可は引き続き、外部の信頼された登録情報と最終的な完全同一性ゲートから得る。

---

## 8. 転送粒度はホスト境界のパラメータである

H3とH4の比較から、中継単位の大きさが、LLMホスト内部の境界を越えて完全一致データを利用できるかどうかへ大きく影響する可能性が示された。

現在の証拠が支持するのは次だけである。

```text
観測した環境での大きな単一試料 = FAIL
観測した環境での小さい8チャンク試料 = PASS
```

次は確立していない。

```text
普遍的な安全最大文字列長
普遍的な最適チャンクサイズ
モデル非依存の閾値
ホスト / ベンダーをまたいで成立する転送規則
```

したがって、チャンクサイズやチャンク数は、アプリケーション固有の意味ではなく、転送方式のパラメータとして扱うべきである。

---

## 9. 汎用転送はまだ未確立

現在のH4 PASSが証明するのは、1種類の不透明な実行カプセル形状に対する、限定された中継転送の基本機構である。

アプリケーション全体で使える汎用実行転送を証明したわけではない。

より強い段階へ進める前に、重要な要件として次が残る。

```text
実行単位に依存しない記述子 / 転送結合
0..N個の実行可能依存物
0..N個の変更不能データ依存物
複数種類の入力結合方式
汎用的な引数 / 呼び出し契約
汎用的な構造化結果契約
動的なチャンク数
チャンク単位の同一性
最終転送対象の同一性
決定論的な転送生成器
ファイルシステム / リソース制限
異なる実行単位形状をまたぐ横断実証
```

代表的な目標:

```text
同じ汎用中継転送 / 実体化処理
-> 単純な固定ファイル入力の実行単位
-> 型付きフィールド + 実行可能依存物 / データ依存物を持つ実行単位
-> アプリケーションが構成した構造化入力を使う実行単位
```

これらが成立するまでは、次の境界を維持する。

```text
限定された実行環境側中継転送の基本機構 = PASS
汎用的な実行単位横断転送 = OPEN
信頼済みホスト全体のエンドツーエンド統合 = OPEN
```

---

## 10. 公開再現性の境界

既存の公開用合成フィクスチャでは、基本的な決定論的転送表現 / 実体化経路をローカルで再現できる。

ただし、今回報告したホスト内部の「呼び出し側コンテキスト -> 実行環境側」中継挙動までは再現しない。

したがって、現時点では次のように区別する。

```text
基本実体化のローカル再現 = 利用可能
ホスト内部中継転送の再現 = ブラックボックス証拠のみ
第三者によるホスト内部中継転送の独立再現 = OPEN
ホスト / ベンダー間の再現 = OPEN
```

今後より強いプロトコル主張を行う場合も、この違いを維持する必要がある。

## 11. 現在の主張範囲

観測済み:

```text
H1 外部転送データを観測 -> 実行環境側への引き渡しはBLOCKED
H2 ローカル添付経路 -> 正本実行 PASS
H3 大きな単一呼び出し側コンテキスト中継 -> FAIL
H4 小分けチャンクによる呼び出し側コンテキスト中継 -> 限定的な複合証拠によるPASS
```

推定:

```text
ホストによるリソース観測
!=
呼び出し側コンテキストでの利用可能性
!=
実行環境側での利用可能性
```

仮説 / 未確立:

```text
汎用的な実行単位横断転送
ホスト / ベンダー間での中継転送の可搬性
普遍的なチャンクサイズ閾値
本番利用可能な信頼済みホスト統合
```
